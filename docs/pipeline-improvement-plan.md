# 字幕管线简化与质量改进计划

## 状态

已实施。正确性相关改动和单元测试已经落地；问题视频的完整回归仍需在批处理恢复后执行。

批处理已通过 `work/yumemita-2026-08-10.stop` 请求在当前视频完成后暂停。本文只描述字幕管线内部修改，不改变下载、上传、渲染、模型选择或现有歌词似然阈值。

## 原则

- 修复应替换旧路径，不在旧路径旁增加另一套补救系统。
- 不增加新模型、新 LLM 阶段、动态阈值或持久化状态类型。
- 一个阶段的输出不改变后续决策时，删除该阶段。
- 歌唱与讲话继续作为可以重叠的证据，不恢复连续 singing episode。
- 只有 `VerifiedLyricSpan` 可以生成歌词字幕或删除重叠讲话。

## 最终主流程

```text
AST + pyannote
-> AcousticPhrase 与 speech 路由
-> Qwen speech ASR / HeartTranscriptor ALT
-> LLM ASR 纠错
-> Forced Aligner
-> 搜索组解析（一个组可确认多首歌）
-> 统一歌词范围验证
-> 统一 speech 质量检查
-> speech / VerifiedLyricSpan 时间仲裁
-> 本地确定性分段
-> LLM 断句与翻译
```

## 1. 一个搜索组可确认多首歌曲

### 问题

`SongSearchGroup` 用最多 35 秒间隔连接 ALT cue，但当前每组只选择一首歌。相邻歌曲、串烧或短讲话分隔的两首歌可能进入同一组，第一首确认后，剩余 ALT 不再搜歌。

### 修改

在一个函数内处理搜索组：

1. 对尚未处理的 ALT cue 使用现有本地歌词匹配。
2. 本地未命中时，使用现有受限联网搜索。
3. 按文本匹配排名依次尝试歌曲候选。
4. 候选至少生成一个 `VerifiedLyricSpan` 后才确认。
5. 确认后移除该 take 已匹配的 ALT cue，再处理剩余 cue。
6. 一轮没有确认新歌曲时结束。

未处理 cue 只是在函数内维护的集合，不写入缓存，不增加新数据类。每个剩余连续段仍遵守当前联网限制；包含多首歌的初始组可能产生多于两次总查询，这是识别多首歌的必要成本。

重复歌词页面先按规范化歌词正文去重，不使用“第一名必须比第二名高固定分差”的规则。

## 2. 一个统一歌词范围验证器

### 问题

当前存在三条歌词恢复路径：

- 锚点间补漏；
- take 前后扩展；
- AcousticPhrase 邻近恢复。

它们对音频范围、stem 来源、候选竞争和审计的处理不同。锚点间补漏还会用缺口中心固定约 20 秒音频验证可能长达 60 至 80 秒的歌词。

### 修改

删除三套恢复实现，统一为一个内部函数。输入仅包括：

```text
歌曲
待验证歌词行范围
对应音频起止时间
可选左锚点
可选右锚点
```

该函数：

1. 使用传入的真实音频范围，不另取中心窗口。
2. 超过 pySHIRO 窗口上限时，按歌词顺序切成连续小块。
3. 为每块从原视频生成对应 Demucs 人声 stem。
4. 使用同一个 pySHIRO 候选验证实现。
5. 返回成功的 `VerifiedLyricSpan` 和逐块审计。

调用方式只有范围不同：

- 初始 ALT 锚点：使用 cue 的真实范围。
- 两个锚点之间：使用 `[左锚点结束, 右锚点开始]`。
- 锚点前后：使用歌曲 take 内尚未验证的相邻范围。

不新增 `LyricProbe` 数据类、缓存或路由。临时 stem 只是函数内部文件。恢复阶段不补跑 ALT；歌曲和顺序已经由现有锚点确定，ALT 不应成为第二套歌词验证器。

## 3. 一个统一 speech 质量入口

### 问题

重复循环、混合语言、异常文本密度和 Forced Aligner 健康度目前只完整应用于 `asr_route=song_speech_fallback`。pyannote 将歌声直接判为普通 speech 时可能绕过检查。

### 修改

所有 Forced Aligner 后的 speech 都调用同一个质量函数和审计函数：

- 所有 speech：检查重复循环、时间单调性、有效单元覆盖、零时长比例、异常空隙和极端文本密度。
- 与 singing 或强 music 证据重叠时：额外检查明显的混合语言异常。

质量检查不再根据 `asr_route` 选择不同实现。`song_speech_fallback` 仍可表示 ASR 是如何产生的，但不再拥有专用质量逻辑。

先丢弃明显错误的 speech，再与 `VerifiedLyricSpan` 仲裁。最小片段失败只丢弃该片段并记录审计，不终止视频。歌词未验证本身不能证明 speech 错误，日语讲话中的少量英语也不能单独触发拒绝。

## 4. 删除无决策作用的人声 stem 二次 AST

### 问题

人声 stem 的 AST 将 singing 分为 high 或 medium，但两者当前都会进入 ALT，后续搜歌和 pySHIRO 也不采用不同规则。

### 修改

确认 `vocal_score` 没有其他决策调用方后，删除：

- 人声 stem 二次 AST 推理；
- high / medium singing 分支；
- 只为该分类存在的缓存和配置。

Demucs 保留，继续为 ALT 和 pySHIRO 提供人声 stem。首轮原始音频 AST 仍决定哪些区间进入 `AcousticPhrase`。

## 5. 说话人插话形成分段边界

### 问题

本地分段按 speaker 建立轨道后，A 在 B 插话前后的内容可能被合成一条跨越 B 的 cue。

### 修改

构建单 speaker 分段时，时间上遇到另一 speaker 的 cue 就结束当前可合并段。这只是现有合并条件中的一个边界判断。

不同 speaker 的 cue 仍可进入同一个翻译 `TopicBlock`，以保留问答、接话和指代关系。真实同时讲话的重叠处理不变。

## 6. 知识库更新失败时使用旧库

流水线启动时仍按 24 小时规则执行增量更新：

```text
更新成功 -> 使用新库
更新失败且旧库可读 -> 记录错误并使用旧库
更新失败且旧库不可读 -> 终止流水线
```

只保留上述一个异常分支，不增加重试状态、降级等级或额外缓存。日志记录失败来源、异常和旧库更新时间。

## 后续性能简化

以下内容不与正确性修复同时实施：

### LLM 断句 A/B

LLM 断句在实际视频中耗时约 13 至 55 分钟。固定抽取独播、多人对话、SC 朗读和快速口语样本，对比：

- 本地分段直接翻译；
- LLM 断句后翻译。

若 LLM 断句没有稳定优势，直接删除；不再新增场景判断规则。

### RAG 批量重排

若性能日志确认 cross-encoder 是显著瓶颈，再使用模型现有 batch 接口一次处理多个 TopicBlock。召回、评分和结果不变，只减少模型调用批次。

## 实施顺序

1. 统一歌词范围验证器，删除三条旧恢复路径。
2. 搜索组内处理多首歌曲，并延迟到声学验证后确认候选。
3. 统一 speech 质量入口。
4. 修复说话人插话边界。
5. 删除人声 stem 二次 AST。
6. 加入知识库更新失败后使用可读旧库的简单分支。
7. 使用问题视频完整回归。
8. 根据测量结果决定是否删除 LLM 断句或批量化 RAG。

## 回归测试

- 同一 35 秒搜索组内的两首歌曲分别确认。
- 多个站点返回相同歌词时不互相否决。
- 60 秒锚点缺口按真实范围分块并恢复。
- 锚点前后扩展与锚点间补漏使用同一验证函数和审计结构。
- 任一歌词小块失败不影响其他已验证块。
- pyannote 误标的混合语言歌声不会泄漏为 speech 字幕。
- 歌中真实念白仍可保留。
- `A1 -> B1 -> A2` 不会生成跨越 `B1` 的单条 A cue，但三条仍可进入同一 `TopicBlock`。
- 知识更新失败且旧库可读时继续；旧库不可读时终止。

每轮记录歌曲确认数、`VerifiedLyricSpan` 覆盖率、speech 保留和拒绝数、误删讲话数、模型调用次数、墙钟时间及峰值显存。

## 非目标

- 不将整段已确认歌曲直接视为歌词覆盖。
- 不让未经验证的 ALT 删除 speech。
- 不恢复完整 singing episode。
- 不增加新的歌词候选分差。
- 不修改现有 pySHIRO 绝对分数和 margin 阈值。
- 不恢复翻译后校对或译文长度硬重试。
- 不改变评论发布、字幕样式、下载、上传或渲染。
