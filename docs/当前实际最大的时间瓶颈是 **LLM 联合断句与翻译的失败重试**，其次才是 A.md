**第一瓶颈：LLM 重试**

这次翻译阶段共有：

- 14 个最终成功窗口
- **68 次无效响应**
- 11 次窗口缩小

主要错误是译文中仍含日文假名，触发本地目标语言校验。每次失败都意味着：

1. 等待完整 API 响应。
2. 指数退避等待。
3. 重新发送整个窗口。
4. 连续失败后缩小窗口重新处理。

所以虽然单次 DeepSeek 请求通常只需十几至几十秒，累计重试将该阶段拉到了约 22 分钟。这里是目前最值得优化的地方。

**第二瓶颈：ASR 区域过碎**

音频分析最终产生了 `1529` 个 ASR 区域，而且是串行识别。很多重叠分轨只有 3–5 秒，仍要分别执行：

```text
ffmpeg 截取 → Qwen ASR → Forced Aligner → 写缓存
```

单个很快，但固定启动、文件读写和模型调用成本累计明显。这也是此前看到 `asr-analysis-chunks` 频繁创建短文件的原因。

优化方向是把相邻、同说话人、同来源的短区域批量处理，或者直接以内存波形输入模型，减少 1529 次 ffmpeg 子进程和磁盘往返。

**其余阶段**

- 音频分析约 6 分钟，包含 pyannote、AST、MossFormer2 和声纹匹配，属于合理但仍可优化的 GPU 阶段。
- x264 `medium` 压制约为 `9.7x` 实时速度，表现正常。
- 下载和上传在当前网络下都不构成瓶颈。
- 有歌曲的视频还会增加 Demucs、OCR、搜索和歌词核验时间，但一般仍不及大量 LLM 重试。

因此当前优化优先级应当是：

```text
减少 LLM 无效响应/重试
  > 合并短 ASR 区域并减少磁盘 I/O
  > 并行或批量 ASR
  > 音频分析优化
  > 视频编码
```

最突出的问题不是 GPU 算得慢，而是 **LLM 68 次失败重试，加上 1529 个碎片化串行 ASR 任务**。
